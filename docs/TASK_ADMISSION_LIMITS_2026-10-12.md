# 任务准入限制与累计用量边界（2026-10-12）

当前实施的是不用迁移的逻辑任务数量和提交频率保护。它不是供应商请求计费、token账本或人民币费用上限。所有验证使用合成材料和测试网关，未启用真实付费调用。

## 已实现的配置

| 环境变量 | 默认 | 范围与含义 |
|---|---:|---|
| PLATFORM_MAX_ACTIVE_TASKS_PER_USER | 32 | 0～1000；跨工作空间、人物/知识两队列，按原始creator累计未结束任务；0关闭 |
| PLATFORM_TASK_SUBMISSIONS_PER_MINUTE | 60 | 0～10000；单API进程中每creator的滚动60秒准入操作数；0关闭 |
| PLATFORM_TOTAL_TASK_SUBMISSIONS_PER_MINUTE | 120 | 0～10000；单API进程所有creator的滚动60秒操作数；0关闭 |

配置在PlatformProperties中统一校验，application.properties提供默认值，.env.example和compose映射一致。没有编辑用户.env、OS或生产配置，当前18080服务也未重启。已有大数据分页测试显式关闭三项限制，保持分页场景205条不变；独立限额测试明确打开小额度，不能把分页测试豁免当功能验证。

TaskAdmissionService在现有业务事务内运行，复用ResourceRepository对原创建者app_user行加锁，TaskAdmissionRepository一次统计job/ persona_job状态。创建、人物/知识手动重试、知识任务resume都调用同一准入服务，管理员替他人操作仍占原creator的额度；改变工作空间、任务种类或操作者不能借用别人的名额。人物重试取得任务锁后重新读取FAILED状态，避免旧状态重复入队。

## 释放和重传规则

| 变化 | 未结束名额 | 滚动频率计数 |
|---|---|---|
| 新任务事务提交 | 占1个 | 占1次 |
| 人工重试FAILED | 重新申请1个 | 申请1次 |
| PAUSED → QUEUED | 原名额继续占用，不重复占 | 申请1次，防止暂停/恢复反复启动绕过 |
| QUEUED/RUNNING → PAUSED | 继续占用 | 不退款 |
| 最终SUCCEEDED/FAILED/CANCELLED | 释放逻辑名额 | 原已提交操作继续计入60秒窗口 |
| 暂时失败自动重排、有效租约release、过期接管 | 原名额继续占用 | 同一已准入任务不重复计次，仍受既有最多3次自动尝试约束 |
| 已结束任务归档/恢复历史 | 不变成活跃任务 | 不退款；后续retry重新检查 |
| 创建或恢复事务明确回滚 | 无新任务/状态写入；聊天消息一并回滚 | 退款对应临时ticket，全局及用户计数都返还 |
| 事务完成未知 | 以数据库状态为准 | 保守保留计数，不自动退款 |

成功任务创建后的取消、失败或删除不能立即清空提交计数。三个稳定429错误码为user_active_task_limit、user_task_submission_rate_limit、platform_task_submission_rate_limit。两套页面均有中文解释；实际问答HTTP错误解码和表单回归证明429后输入保留、按钮恢复、不启动轮询。

## 已验证与局限

先新增10项服务/HTTP/事务测试，在旧实现全部失败；跨队列并发6次创建全部被接受，预期只有1个名额。修复后19项针对性Java测试全部通过：跨队列/跨空间/原creator、暂停保留、人工重试/历史恢复、最终失败和取消释放、自动重排和租约归还保留、事务退款、全局频率、精确分钟边界、零配置、并发全局预留、重启非持久特性，以及聊天拒绝不残留消息。

完整scripts/verify.py --e2e通过Java120、Worker31、7组前端、7个JS语法、86个Java架构守卫和人物/知识HTTP E2E；固定词面20/20、语义探索0/3未改。源码校验与日志索引见research/task-admission-2026-10-12.json，完整日志/tmp/distilly-task-admission/full-verify.log。

未结束容量取现有数据库状态，不因Worker重启消失；同一数据库的creator行锁用于串行化准入。当前只实测H2事务与单API内并发，不宣称PostgreSQL/多API云部署已验收。滚动窗口是单API进程内计数，重启清零，多API不共享。未限制认证、轮询等所有HTTP请求，也不是存储量上限。

Worker仍保持现有串行运行，未增加进程或供应商并发。启用更多Worker会提高实际并发；用户取消可能已释放逻辑名额，而旧供应商请求尚未真正停止。因此本功能不能保证实际供应商同时请求数。一个任务可以产生多阶段、多个材料分块及自动重试，任务操作数不能等同模型调用数。

输入字符上限、保守上下文预算、聊天显式max_tokens及输出格式/正文大小校验是不同的限制。批次十已为所有文字阶段补齐显式输出token预算和截断终态拒绝，详见MODEL_OUTPUT_BOUNDS_2026-10-12.md；图片音频协议独立。字符/读取字节/校验上限并不证明真实token使用或费用上限；模型价格未知时不换算人民币。

## 真正持久额度的最小追加设计（仅提案，没有SQL文件或迁移）

如果要把“重启后仍有效、删除任务不可绕过”的任务操作额度变为承诺，最低需要在下一可用追加迁移中增加task_admission_event表：operation_id主键、actor_id、task_family、task_id、operation(create/retry/resume)、accepted_at。task_id不外键到可删除任务表，避免删除会话/人物把额度历史一起级联删除；actor_id可引用保留的app_user。增加(actor_id,accepted_at)索引。准入事件与业务状态在同一事务提交，重放同operation_id不重复计数，继续锁既有app_user行；窗口和配额阈值以明确的数据库时间/周期定义核验。

若还需要多API共享的严格全局额度，再加一个task_admission_guard单行表，保存global锁记录，所有准入按一致顺序锁该记录与用户行后检查事件总数。否则多个API对总事件的并行count/check/insert仍可能超额。二者均须先确认迁移及旧库升级/恢复测试，不在本批执行。

回滚策略：追加表不修改旧任务/用户字段，旧版本代码可忽略新表。回滚代码前应先暂停新任务准入，因为旧代码不会继续执行新持久额度；保留事件表以便审计和恢复，不能自动DROP或清空它。新旧API混跑也不能称额度可靠。

以上持久表仍只计准入操作。真实费用保护还需按供应商实际请求记录stage/chunk/lease/request_id及输入/输出usage，保留价格版本和货币，发起调用前预留上界，响应明确后结算，未知结果不擅自退款。没有供应商价格/usage契约和逐请求幂等时，不承诺人民币硬上限。此类账本、预算行和Worker协议是另一个需明确评审的数据变化，当前不迁移、不调用供应商。

当前继续先编码成熟、之后再部署；本地语义模型安装已搁置，不购买云资源、不部署、不上传材料。
