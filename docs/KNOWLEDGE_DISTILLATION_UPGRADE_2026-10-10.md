# 知识蒸馏升级方案

日期：2026-10-10。依据：当前源码复核；承接 10-09 流程审查。本文是待实施方案，没有修改运行服务或业务数据。

## 当前判断

可靠执行的底座已经具备：专题标题进入模型、段落/句末边界切分与重叠、冻结输入、分块结果持久化、租约和执行指纹、生成前规模预检、不可变发布版本。10-09 文档中“缺少断点/预检”的判断已被后续代码实现取代，不能继续列为未实现。

主要短板是知识质量与治理：每块独立生成 section/text/evidence；服务端把新条目追加到旧快照，只有精确文本去重；没有跨块综合、条件结构、冲突处理和逐条审核。已审核知识的手工修订已有，但不能代替发布前的候选编辑。

| 优先级 | 当前源码事实 | 用户影响 |
|---|---|---|
| P1 | PublishedKnowledgeService.validateEvidence 按 chunk 序号 ×6000 取原文；MaterialChunker 已采用可变边界与重叠 | 第二块起合法证据可能被误拒，阻塞手工修改；必须统一证据定位 |
| P1 | Model.work_system_prompt 拼接上游“个人工作能力/风格”提示词，再追加专题知识规则 | 目标混杂；换成项目自有、单一目标且版本化的提取协议，上游提示词不直接修改 |
| P1 | WorkTaskService.complete 按 section+text 去重，命中后直接丢弃新条目 | 新来源丢失；同义重复、相反结论和条件变化都可能一起发布 |
| P1 | KnowledgeService.review 只接受全版本 approve/reject | 一条错误就要拒绝整批，无法把可用条目先发布 |
| P2 | Worker 收集全部生成结果后限制300条；服务端还计算继承知识后的300条 | 预检只是估计，没有真正分配预算；失败可能发生在大量模型调用之后 |
| P2 | Worker.answer 按中文单字排名，零分也可能进入上下文 | 蒸馏质量与检索效果混淆，回答质量需单独验收 |

来源校验目前只证明引文存在，不能证明引文支持结论。新方案继续区分原文存在校验、模型支持检查和人工审核。

## 目标过程与产物

| 阶段 | 具体动作 | 保存的产物 / 页面反馈 |
|---|---|---|
| 1 专题定义 | 设定目标问题、范围、排除内容和输出类别，标题不再承担全部约束 | 版本化专题配置；生成弹窗可查看和调整 |
| 2 材料准备 | 保留原文；标注章节、来源日期/版本与切块位置；预检规模及预算 | 冻结 manifest：材料摘要、范围配置、切分策略、模型与提示词策略 |
| 3 事实提取 | 每块提取材料明确支持的事实及局部步骤，识别无关内容和信息缺口 | evidence spans + atomic facts；逐块断点复用 |
| 4 经验整理 | 按问题/对象/条件组织跨块事实，形成可执行经验；缺失字段明确为空 | 事实、操作流程、问题案例、经验规则等类型的候选条目 |
| 5 新旧对比 | 先做确定性去重，再提示语义相似和潜在冲突；保留来源 | 新增、补充依据、可能重复、条件变化、可能冲突、无相关内容 |
| 6 逐条审核 | 接受、修改、排除、确认合并或替代；正文与原文并排显示、定位高亮 | 保存审核草稿；负责人单独执行发布，展示最终差异 |
| 7 发布与评测 | 原子生成不可变版本，刷新当前知识索引；记录审核原因和抽审结果 | 已审核知识仍保留独立搜索/分页/手工修改入口 |

任务展示阶段进度：提取 x/y 块 → 整理 x/y 组 → 对比 → 待审核。分块进度不冒充整项任务完成度。空结果明确说明无相关知识；只有依据补充时也显示差异，不制造“新增知识”。

## 知识条目如何升级

保留旧 text/section/evidence 可读，新增契约版本与可选字段：

- `type`：事实 / 流程 / 案例 / 规则；`title`：条目名称；`text`：兼容展示与检索的正文。
- `scope`：适用对象、前置条件、时间和系统版本；未知值为空，不由模型猜测。
- `steps` / `outcome` / `caveats`：按类别需要填写；没有实测结果不能宣称有效。
- `evidence_refs`：来源材料、冻结块摘要、原文起止位置、引文；校验状态与人工判断单独保存。
- `relations`：支持、补充、可能重复、可能冲突、替代；关联到具体知识修订，而非仅条目ID。

例如“设置720分钟TTL可以防止重复推送”不能直接整理为“每天只推送一次”。若材料只记录720分钟TTL，就保留“12小时窗口”事实；自然日策略需要另有证据。若材料提供故障与修复过程，可整理成“触发场景 → 排查步骤 → 修复动作 → 已观察结果 → 适用边界”，避免变成无条件经验规则。

## 关键实现约束

**证据统一。** 新证据记录原文 span 与冻结块摘要，提取、候选编辑、发布后修订使用同一领域校验器。历史来源优先回溯产生它的冻结任务载荷：可重算确定性校验，但不按新策略重切旧任务。缺少历史载荷时明确标记无法恢复块定位，并走可审计的人工迁移流程；不能静默改用全文命中冒充原块校验。相同引文出现多次时保存选定位置。

**分阶段生成。** 事实提取不携带整份旧知识；整理按分组与上下文预算运行，对比只提供相关旧条目。每阶段独立保存输入摘要、协议版本、执行指纹及结果；复用租约与幂等回调，暂停/重试只执行缺失阶段。配置变化不能混用旧结果。模型不能自动批准或替代已发布知识。

**去重和修订。** 完全相同条目先合并有效来源，不丢弃证据；超过来源显示上限时按需分页，不能截断持久化依据。相似条目及矛盾由模型提示、人工确认。时间/适用范围不同可能是并存规则，不是必然冲突。手工修订过的正文参与新旧对比，禁止后续蒸馏自动恢复旧说法；替代须展示差异并明确确认。

**审核发布。** 保存草稿使用 review_revision 乐观锁；发布核对 expected_published_id、草稿修订号和候选状态，一次事务保存已接受条目与审计。修改正文保留依据；不支持的修改必须排除或另走明确标识的人工知识机制。EDITOR 可按现有空间权限编辑候选，OWNER 才可批准；VIEWER 不接触未发布草稿及原材料。

**规模治理。** 先分开统计原始事实预算、候选预算、发布容量；达到预算时提前提示拆分任务，禁止静默丢弃。中期新增 knowledge_item、knowledge_item_revision、evidence_span、version_member、review_draft 等对象，版本保存成员关系；追加迁移兼容历史 JSON 快照。扩大300条前先完成独立存储，避免复制全文增长。

保持现有模块化单体：knowledge 管领域规则与版本，task 管执行/租约，worker 管模型计算；复用共享设计系统、搜索→表格→分页、原生 dialog。预览端口保持18080。

## 2026-10-11：字符切分升级实施

已实现 `structure-overlap-v2`，用于新建任务；已冻结任务继续使用原 payload 和 input_digest，历史版本不重切。

- 单块仍上限6000个 UTF-16 单位；按章节、空行段落、行、中英文句末寻找边界。原文不清洗、不拼接，保存精确 start_offset/end_offset。
- 识别常见 Markdown 围栏代码块（反引号/波浪线）、连续表格行、列表及缩进续行；结构块可容纳时整体移到下一块。标题尽量与首行内容或紧接的结构块一起保留。
- 超过上限的结构块继续按上述边界拆分；无可用边界的超长行才按上限截取。支持 CRLF、含空格空行；避免拆开 UTF-16 代理对和 CRLF。
- 重叠以240单位为目标，优先对齐句子/行，最多480单位；如果重叠会拆开可完整保留的结构块，则缩减或取消重叠。每块必须增加原文覆盖，不允许重复片段导致停滞。
- 引文校验共用 MaterialEvidence。发布后手工修改沿版本继承链追溯条目最初生成的任务，再对其冻结块核验；带偏移的历史任务使用原偏移，最早无策略标记的任务才使用固定6000偏移。缺失来源任务或原文/分块不一致时拒绝，不用“全文有同一句话”替代原块验证。

这是确定性的结构切分，未接入模型语义分段，也不是完整 CommonMark 解析器。超长结构跨块时不补造代码围栏、表头或标题到证据正文；组合 emoji 的字素簇保护、按模型 token 预算切分和跨块经验整理仍待后续实现。

新增回归覆盖：完整代码/表格/列表、标题与代码关联、CRLF与代理对、超长/未闭合代码块、20万字连续文本、混合结构覆盖与确定性；旧固定/v1分块编辑、新长材料多次修订与增量版本、原文存在但不在原块的引文拒绝。HTTP E2E 增加长材料预检、分块生成、发布和第二块知识修改。
