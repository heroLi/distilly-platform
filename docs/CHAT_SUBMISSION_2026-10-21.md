# 原始消息提交：丢响应恢复与请求幂等

从原工作区和独立续做分支 `resume/text-cost-gate-20261021` 的 `6c83b3ff84a7dc17d22341593a6644380f4c64f1` 干净基线开始，无并发编辑。旧恢复文件、候选和已提交证据保留。本轮真实模型调用 0，不改费用安全闸。

## 复现与契约

旧版浏览器复现了“消息已经保存→响应丢失→任务已停止→再次发送原输入”，产生两条相同用户消息和两个任务。原任务重试的幂等不能解决这个原始提交问题。基线截图、结果和原 JAR 单独保存在忽略目录 `data/resume-20261021/chat-submission/`。

新界面为每次明确发送生成 UUID `request_id`。服务器在会话锁和同一事务内创建用户消息、任务及 `chat_submission` 回执。约束为 `(conversation_id, request_id)` 唯一；同编号、同规范化文本与同图片重复/并发请求返回原任务和原回执，不重新入队、不重复消息。相同编号但内容不同返回 409 `submission_conflict`。原任务已经失败、取消或完成也保持原身份，不由提交重放复活。任务重试仍使用上轮的显式任务重试入口。

操作编号按私人会话隔离；不同人物、会话和用户可分别使用相同 UUID，不能取得别人的回执。每次 POST 和 GET 都先执行会话所属用户、空间成员和人物可访问检查，不因缓存命中跳过权限。`GET /api/conversations/{id}/submissions/{request_id}` 只返回 `request_id/message_id/job_id/status=ACCEPTED`，不返回输入摘要、正文、图片或凭据。未找到返回 404 `submission_not_found`；这只表示读取时未找到，不能推断旧请求永远不会提交，因此显式重试仍必须使用同一编号。

V009 是追加迁移，旧 V001–V008 未重写。回执保存规范化输入 SHA-256 和消息/任务引用，不复制正文；会话删除时先清理回执，再删除任务与消息。回执与对应会话同生命周期，不用短 TTL 让迟到重放重新建消息。既有无编号 API 保留兼容，其请求不具备本次新增的提交幂等；新界面始终携带编号。

## 页面恢复

浏览器仅在本应用专用、按用户/空间/人物/会话区分的 tab sessionStorage 中保存操作 UUID 和内容摘要，不保存文本、图片或令牌。发送前必须成功保存编号；存储/摘要不可用则不发送。页面刷新或离开/返回时不自动 POST，显示“核对本次发送”。已保存则 GET 恢复原回执；未查到时允许显式“重试本次发送”，但须重新输入相同原内容，继续使用原编号。内容不同不发送。

确认保存后，仅清除仍与原输入相同的草稿；新草稿保留。旧响应被人物、用户、会话、epoch、选择序号和页面生命周期隔离；切换新会话后晚响应不会清除其草稿或显示旧消息，原操作仍可回到原会话核对。权限丢失时清理当前操作记录并禁止发送；退出清理本应用操作元数据。这里没有持久保存草稿正文，关闭标签、退出或清除浏览器存储后不能承诺恢复操作编号；应先核对服务端交流历史，不盲目再发。
